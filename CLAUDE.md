# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview
Flask web app that logs a user in through Zerodha Kite Connect v3 (`kiteconnect` Python SDK), then shows a dashboard for bulk-downloading historical candles for all NSE equity stocks and selected NSE indices (NIFTY 50 spot etc.) (https://kite.trade/docs/connect/v3/historical/) and watching the job's progress live. It also runs a daily F&O job for NIFTY (Kite NFO) and SENSEX (Kite BFO) (1-minute candles with OI for every live future and option, saved in the Accelpix layout) from a dashboard card or `nifty_daily.py`, and checks each saved day against the exchange's F&O bhavcopy, NSE's for NIFTY and BSE's for SENSEX (dashboard "Bhavcopy check" card or `nifty_bhav.py`). The UI calls itself "Kite Backfill". Everything runs locally on one machine.

## Commands
- Install: `pip install -r requirements.txt` (flask, kiteconnect, pandas, pyarrow, openpyxl, tzdata, pytest)
- Run: `python app.py`, which serves http://127.0.0.1:5000. Debug is off, so neither `.py` nor template edits are picked up until the server is restarted (templates are cached). Restarting stops a running download; Resume is safe.
- Tests: `pytest` (`pytest.ini` sets `pythonpath = .`). `tests/test_fno.py` covers `backfill/fno.py`, including a full run against a fake `KiteConnect` (`FakeKite`: token 13 returns zero-volume candles, 14 none, 31 fails), a subprocess run with `TZ=UTC`, zero-volume keep/skip, `refetch_no_trade` and inspect (writes nothing). `tests/test_bhav.py` covers `backfill/bhav.py` (parsing, units, statuses incl. ZERO_VOLUME_IN_KITE, buckets, severity, banners, dashboard routes) and `backfill/bhav_export.py` (CSV/Excel contents, 404s, nothing written, CLI exports); `tests/test_fno_loader.py` the backtest loaders. `tests/test_fno_entrypoints.py` covers the F&O dashboard route and the CLI. `tests/test_sensex.py` covers SENSEX: a full BFO `run_daily` with a BSE bhavcopy (fake Kite, stubbed fetch), BSE fetch answers (CSV, HTML page = not published), units, exports, `load_eod`, routes and CLI, and `weekly_expiry_weekday` per underlying. `tests/test_dhan.py` covers Dhan sign-in, `tests/test_dhan_api.py` the Dhan client (fake `requests`), `tests/test_dhan_fno.py` a full `run_daily` on Dhan (`source="dhan"`) and the Dhan routes, `tests/test_dhan_sensex.py` Dhan SENSEX (BSE_FNO list and segment, trim to BSE's bhavcopy, the spot holiday check, re-download, page, routes and CLIs), `tests/test_dhan_parity.py` the Kite features on Dhan (bhavcopy check after each day, refetch_no_trade and its route, `nifty_daily.py`/`nifty_bhav.py --source dhan` incl. inspect, the loaders); none touch the network or `.env`. Tests stub `load_env`/`save_env`/`keep_zero_volume` wherever a route or CLI reads them, so the real `.env` is never read or written (a test that only passes with a real token in `.env` is a bug). No test may hit Kite or NSE over the network. No linter is configured.
- Daily F&O CLI: `python nifty_daily.py (YYYY-MM-DD | --missing | --refetch-no-trade YYYY-MM-DD) [--folder PATH] [--speed 2.5] [--underlying NIFTY|SENSEX] [--source kite|dhan] [--keep-zero-volume | --no-keep-zero-volume]` (a date or --missing is required; the date is never defaulted). Diagnostics that write nothing (no folder check, no lock): `--inspect CONTRACT YYYY-MM-DD` prints Kite's raw candles plus the saved bhavcopy row, `--inspect-missing YYYY-MM-DD` does it for every MISSING_IN_KITE contract of the day's bhav_compare.csv and prints a table with Result ZERO_VOLUME_CANDLES / NO_CANDLES / TRADED. Exit codes: 0 finished or holiday, 1 failures or not run, 2 token missing or invalid, 3 date outside the window. argparse errors are changed to exit 1 so that 2 always means a token problem. `--source dhan` (`sign_in()`): NIFTY or SENSEX, speed up to 5, token from `dhan_api.token_ok(load_env())` (missing/expired -> 2), `DhanClient.profile()` (TokenException/PermissionException -> 2) and `data_plan_error()` (not Active -> 1); every mode, inspect included, then runs with `kite=client, user=, source="dhan"` on the Dhan folder and lock, and inspect output is relabelled Dhan. Do not run it against real Kite or Dhan unless the user asks. The user runs it manually; no cron or scheduled task is set up, and none should be added.
- Bhavcopy CLI: `python nifty_bhav.py (YYYY-MM-DD | --missing | --export YYYY-MM-DD [--csv] | --export-days) [--folder PATH] [--bhav-file PATH] [--underlying NIFTY|SENSEX] [--source kite|dhan]` (`--source dhan`: the Dhan folder and lock) (date or --missing required; --bhav-file needs a date). `--export` saves the day's Excel report (`--csv`: all contracts) into `<date>/bhavcopy/exports/`, `--export-days` the all-days CSV into `<UNDERLYING>_FnO_1min/`; both print the path, take no lock and exit 1 when there is no check. Exit codes: 0 OK, 1 differences or not run, 4 not available (404). Run manually; no cron, as with the Kite job.
- To check routes quickly, use Flask's test client: `from app import app; c = app.test_client(); c.get('/')`. Importing `app` creates or updates `.env` (see below).
- Pages behind login can be rendered without Kite by faking the session: `with c.session_transaction() as s: s["access_token"] = "x"; s["user"] = {...}`. To preview the UI in a browser, run a scratch script that imports `app`, adds a route setting those session keys, and fills `backfill.job.JOB` with sample values, then serves on another port (e.g. 5001). Do not start a real download from it. For screenshots, also override `auth.credentials` to return `("", "")` so the sign-in page doesn't show the saved key.

## Architecture
- Code layout:
  - `app.py` only creates the Flask app, sets the secret key and registers the three blueprints.
  - `config.py` holds paths and the `.env` helpers (`load_env`, `save_env`, `credentials`, `dhan_credentials`, `secret_key`, `data_dir`, `weekly_expiry_weekday`, `keep_zero_volume`) and the default `KEEP_ZERO_VOLUME`.
  - `auth.py` is the `auth` blueprint: `/`, `/login`, `/callback`, `/logout`.
  - `dhan.py` is the `dhan` blueprint: `/dhan`, `/dhan/login`, `/dhan/logout`, `/dhan/dashboard`, `/dhan/fno-window`, `/dhan/fno-start` (Dhan sign-in and the Dhan F&O page; see below).
  - `dashboard.py` is the `dashboard` blueprint: `/success`, `/download/*` (incl. `/download/fno-start` and `/download/fno-window`), `/fno/*` (bhavcopy check), `/browse-folder`.
  - `nifty_daily.py` (repo root) is the CLI for the daily F&O job.
  - `nifty_bhav.py` (repo root) is the CLI for the NSE bhavcopy check (`backfill/bhav.py`).
  - The `backfill/` package is the download engine and has no Flask imports. It contains `job.py` (`JOB`, `JOB_LOCK`, `STOP`), `fetch.py` (`INTERVALS`, `make_chunks`, `RateLimiter`, `fetch_chunk`, the stop exceptions), `instruments.py` (equity/ETF filter, `INDEX_CHOICES`, `is_index`), `storage.py` (`run_key`, `job_run_key`, `check_folder`, candle files, `progress.sqlite`, `errors.log`), `runner.py` (`bulk_download`), `fno.py` (daily F&O job), `dhan_api.py` (`DhanClient`, a Kite-shaped DhanHQ v2 client, and `fetch_profile`), `bhav.py` (NSE bhavcopy check), `bhav_export.py` (downloads of the check) and `fno_loader.py` (reads saved F&O days back for backtests); see below.
  - Templates use blueprint endpoint names in `url_for`, e.g. `auth.login` and `dashboard.download_start`.
- Templates extend `templates/base.html`, which contains the shared CSS (dark theme, Manrope font) and loads React 18 (UMD, cdnjs) and `htm` (unpkg) from CDNs: no Node, no build step, no static files. Each page passes its data to React as JSON in `<script id="boot" type="application/json">{{ ...|tojson }}</script>` and renders into `#root` with htm tagged templates. The React script bodies are wrapped in `{% raw %}...{% endraw %}` because htm's `${{...}}` style objects clash with Jinja; use `className`/camelCase SVG attributes, not `class`/`stroke-width`. `base.html` also defines shared `Toasts`, `useToasts`, `Logo` and `BrokerTabs` (the Zerodha / Dhan tab links at the top of both sign-in cards, `/` and `/dhan`). The UI needs internet access to load React and fonts.
- Login flow: `GET /` shows the sign-in page (`login.html`) for the API key and secret. `POST /login` saves them to `.env`, then redirects to `KiteConnect.login_url()`. Zerodha redirects back to `GET /callback?request_token=...&status=success`, and `generate_session()` exchanges the token for an `access_token`. That token and the user details go into the Flask session. Then `/success` shows the dashboard (`success.html`), and `/logout` calls `invalidate_access_token()` and clears the session. Errors come back as `?error=` and are shown on the page (inline on sign-in, as a toast on the dashboard).
- The Redirect URL registered in the Kite developer console must be exactly `http://127.0.0.1:5000/callback`.
- Dhan sign-in (`dhan.py`, `dhan_login.html`): the user pastes a Client ID and an access token generated on web.dhan.co (no API key / redirect flow). `POST /dhan/login` (blank token with unchanged Client ID re-checks the saved one) calls `dhan_api.fetch_profile()` (`GET https://api.dhan.co/v2/profile`, header `access-token`); the returned `dhanClientId` must equal the entered Client ID. It saves `DHAN_CLIENT_ID`, `DHAN_ACCESS_TOKEN` and `DHAN_TOKEN_EXPIRY` (`parse_validity()` turns Dhan's `tokenValidity` "DD/MM/YYYY HH:MM", IST, into ISO); `session["dhan_user"]` holds client id and `dataPlan` (not the token). Then `/dhan/dashboard?dhan=1`. `/dhan/logout` removes the token keys locally only. `dhan.status(env)` (connected = token present and expiry, IST, in the future) feeds the Dhan pages and the Kite dashboard's account menu (`boot.dhan`, with "Open Dhan F&O"); the Kite dashboard passes its own `load_env()` so tests' stubs cover it. Errors never include the token. Kite and Dhan sessions are independent; `/browse-folder` accepts either.
- Dhan F&O page (`/dhan/dashboard`, needs a valid Dhan token): renders `success.html` with `mode="dhan"` and `broker` (`name`, `maxSpeed` 5, `defaultSpeed` 4, `urls.fnoWindow`/`fno`/`page`); in that mode `App` shows `FnoCard` + `Live` + `Feed` + the banners and `BhavCard` (no Planner), a `DhanMenu` plus a visible Log out button (`.nav-actions`, `/dhan/logout`), and `FnoCard` shows the same rows and buttons as on Kite (Re-check no-trade included; terminal hints add `--source dhan`). Every bhavcopy fetch sends `Q` (`underlying` plus `source: "dhan"` on the Dhan page), and `brand()` shows Kite wording from the check (lines, statuses, headers) as Dhan there. Kite mode passes `broker` with the Kite URLs and max 3, so it renders as before. The F&O card's texts are the same in both modes (broker name from `B.name`); the only intended process difference is the Dhan trim to the bhavcopy (`trim_to_bhav`), plus Dhan's speed limit, data-plan check and folder. `dhan.py` passes `weekly_expiry_weekday(underlying)` like the Kite routes. `/dhan/fno-window` (live expiries from Dhan's list, cached per IST day in `dhan.LIVE`, history from the Dhan folder) and `POST /dhan/fno-start` (`date`, `date_from`+`date_to`, `missing=1`, or `refetch=1` with the Kite route's refusals, `speed` 0 < s <= 5, `folder`, `keep_zero`; checks the token and refuses unless the profile's data plan is Active, then window/too_early, lock, `job_begin`) run `fno.run_daily` / `run_missing` / `refetch_no_trade` in a thread with `kite=DhanClient(token)` and `source="dhan"`. The token rule (`dhan_api.token_connected`/`token_ok`) and the plan check (`data_plan_error`) live in `backfill/dhan_api.py` so the CLI shares them without Flask. Stop and status reuse `/download/stop` and `/download/status`.
- `backfill/dhan_api.DhanClient` implements what the F&O job uses from KiteConnect: `profile()`, `instruments(exchange)` (Kite's NFO/BFO mapped by `SEGMENT_OF` to `GET https://api.dhan.co/v2/instrument/NSE_FNO` or `/BSE_FNO`; each row's `exchange` is the segment, and `historical_data` sends the segment remembered per security id, also learned by `learn()` from a saved list; FUTIDX/OPTIDX rows as Kite-style dicts: `name`=UNDERLYING_SYMBOL, FUT/CE/PE from OPTION_TYPE, `expiry` from SM_EXPIRY_DATE, `strike`, `tradingsymbol`=`SYMBOL_NAME#SECURITY_ID` (Dhan's SYMBOL_NAME is the same for every expiry of a month, e.g. `NIFTY-Oct2026-25000-CE` for 13, 19 and 27 Oct; keyed by it alone, weeklies were written into the monthly file on 2026-10-07), `instrument_token`=SECURITY_ID; missing columns raise a clear error) `spot_token(underlying)` (`SPOT_IDS` NIFTY 13, SENSEX 51 on IDX_I, instrument INDEX; for the holiday check) and `historical_data()` (`POST https://api.dhan.co/v2/charts/intraday`, `interval` "1", `oi`, IST "YYYY-MM-DD HH:MM:SS" bounds; column arrays turned into candle dicts with IST datetimes). Errors are raised as kiteconnect exceptions so `fetch_chunk` treats them like Kite's: 401/DH-901 TokenException, DH-902 PermissionException (both stop the job), 429/DH-904 code 429 (rate halves), 5xx/DH-908 NetworkException (retry), DH-907/"no data" -> no candles, other 4xx InputException (contract FAILED).
- `run_daily(trim_to_bhav=None)` (on for Dhan, off for Kite) calls `trim_contracts()`: `bhav.listed_names()` gives our names of every contract of the underlying in the day's bhavcopy (saved `<day>/bhavcopy/nifty_bhav.csv`, else `fetch_bhav(budget=bhav.TRIM_BUDGET)` = 30 s for home page, tries and waits together, `BhavTimeout` after that; the download is saved like `run_bhav` does) and only those contracts are kept, traded or not; without it (404, error, "bhavcopy fetch timed out") the full list is used and run.log says why. `fno.py` takes `source` ("kite" default, "dhan") in `fno_root`/`fno_folder` (`FOLDERS`: `<UNDERLYING>_FnO_1min` vs `<UNDERLYING>_FnO_1min_Dhan`), `read_expiries`, `record_expiries`, `load_window`, `holidays_logged`, `missing_dates`, `acquire_lock`, `run_key` (Dhan: `fno-dhan:NIFTY:NSE_FNO:<date>`), `exchange_of`, `job_fields` (sets `JOB["source"]`, reset per job via `COUNTERS`), `run_daily` and `run_missing` (which also accept a ready `kite=`/`user=`). The default keeps every Kite folder, key and message unchanged. `bhav.py` (`bhav_dir`, `read_check`, `unchecked_days`, `run_bhav`, `list_days`, `compare_rows`, `diff_rows`), `bhav_export.py` (every reader and `export`; `relabel()` renames `Kite*`/`KITE` to Dhan in Dhan output and file names get `_dhan`) and `fno.redownload_contract` (`kite=`, `source=`; `DhanClient.learn()` reads the instrument type from the saved `instruments_NSE_FNO.csv`) take the same `source`. The bhavcopy routes read `?source=` (`fno_source()`; `signed_in(source)`: Kite session, or a valid Dhan token) and pass it on, including to `locked_fno` and `refresh_live_summary`. The comparison files inside a day keep their `Kite_*` column names for both sources. `refetch_no_trade`, `inspect_contracts` (`kite=`, `source=`), the CLIs (`--source dhan`) and `fno_loader` (`source=`) work on both. `tests/test_dhan_bhav.py` covers the Dhan check, exports, routes and re-download.
- Config lives in `.env`, which is gitignored. It is read and written by the hand-written `load_env()` / `save_env()` in `config.py`. `python-dotenv` is deliberately not used. Credentials are read again on every request through `credentials()`, so changing them needs no restart. Keys: `KITE_API_KEY`, `KITE_API_SECRET`, `KITE_ACCESS_TOKEN` (written by `/callback`, removed by `/logout`), `KITE_DATA_DIR` (the last save folder used for bulk download), and `FLASK_SECRET_KEY` (generated automatically on first import; keeps sessions valid across restarts). Optional `WEEKLY_EXPIRY_WEEKDAY` / `WEEKLY_EXPIRY_WEEKDAY_<UNDERLYING>` (MON..SUN; NIFTY TUE, SENSEX THU by default) are used only for the F&O date-window fallback, and optional `KEEP_ZERO_VOLUME` (ON/OFF) overrides `config.KEEP_ZERO_VOLUME` (False; the user switches the default there). `KITE_DATA_DIR` is also the starting folder of the F&O card and the CLIs' default `--folder`. `.env.example` lists the keys with blank values.
- On the login form, a blank secret with an unchanged API key keeps the saved secret.
- The access token is kept in the Flask session cookie and in `.env`. The bulk job reads it from `.env`. Never print or log it or the secret. Kite tokens expire daily, so the user must log in again each day.
- Historical data is included in the paid Kite Connect plan (Rs 500/month). API errors (e.g. an expired session) stop the job or fail chunks; they appear in the live card's status message and in `<folder>/errors.log`.
- Bulk download (`/download/start`, `/download/stop`, `/download/status`): the form takes a "Stocks" checkbox list (`equity` = NSE equity stocks, plus `indices` = any of `INDEX_CHOICES`: NIFTY 50, NIFTY BANK, NIFTY FIN SERVICE, NIFTY MID SELECT, INDIA VIX; at least one required), a save folder (must be an absolute path; it is created and write-tested before the job starts; defaults to `<project>/data`), a start date, an end date (end date not in the future; max `MAX_RANGE_DAYS` = 365 days when equity is ticked, max `MAX_INDEX_RANGE_DAYS` = 20 years for indices only; the UI's "Since 2015" preset is enabled only without equity), `minute` or `day` (EOD), a speed in req/s (default 2.5; server accepts 0 < s <= 3, the UI slider is 0.5 to 3), a file format (`FILE_FORMATS`: `csv` default, or `parquet`), and "Include ETFs" / "Include trade-to-trade" options (shown only when equity is ticked). ETFs are detected by a name/symbol heuristic in `is_etf()`. A single background thread (`bulk_download`) runs the selected parts one after another in one job: indices first (segment `INDICES`, matched by tradingsymbol, in `INDEX_CHOICES` order; NIFTY 50 is token 256265), then equity. `JOB["part"]` holds the current part text ("Indices: NIFTY 50", "Equity: 1,240 / 2,942 stocks"), and the stock/chunk counters cover all parts. Equity is segment `NSE`, type `EQ`, no liquidity filter, then `is_equity()`. `series_suffix()` treats the text after the last `-` as an NSE series only when it is exactly 2 characters, so `BAJAJ-AUTO` and `NAM-INDIA` count as normal equity. Kept: no suffix, plus `-BE`/`-BZ` when "Include trade-to-trade" is ticked (off by default). Everything else is excluded: bonds, NCDs, G-secs, T-bills, SGBs and SME (`-N*`, `-Y*`, `-Z*`, `-GB`, `-GS`, `-SG`, `-TB`, `-RR`, `-SM`, `-ST`, ...). The selected count and breakdown are printed and shown on the page (`JOB["filter_info"]`); the expected count is about 2,000 to 2,300, and more than `MAX_STOCKS` (3,000) refuses to start.
  - Requests: the range is split by `make_chunks()` into Kite's per-request limit (`INTERVALS`: 60 days for minute, 2,000 for day). `RateLimiter` spaces request starts by 1/rate, halves the rate on a 429, and recovers after 20 successes. `fetch_chunk()` retries 429s and network errors with backoff `min(2**n, 60)` s, up to 10 tries, then marks the chunk FAILED. A TokenException or 403 stops the job (`AuthStop`).
  - Progress: `<folder>/progress.sqlite`, table `chunks`, keyed by `(run, symbol, chunk_from)` with `run = run_key()` = `"<interval>:<from>:<to>"`, plus `":csv"` for CSV runs, so switching format re-downloads instead of skipping, plus `":idx"` for the index part, so index and equity progress never mix (equity keys are unchanged from before). `JOB["run"]` is `job_run_key()`: the part keys joined with `" + "`, which the planner mirrors (together with the selection) to detect Resume. Status is PENDING, DONE or FAILED, committed after every chunk. An empty response counts as DONE (counted in `empty`); e.g. index 1-minute windows before ~2015-01-09. Start / Resume with the same selection, interval, dates, format and save folder skips DONE chunks. A second table, `runs` (`run` -> run folder name, start time), is described under Output. After pass 1, FAILED chunks are re-looped until none remain or a pass fixes nothing.
  - Output: each part of a job writes into its own run folder, `run_dir_name()` = `<Equity_stocks|Index_spot>_<1min|EOD>_<from>_to_<to>_started_<YYYY-MM-DD>_<HHMM>` under the save folder. `run_dir()` records it in the `runs` table of `progress.sqlite` (`run` -> `dir`) the first time a run key starts, and Resume reuses it, so a resumed run never splits across folders (runs started before this table existed get a new folder). `JOB["out_dirs"]` lists the folders for the live card, and the planner's hint mirrors the name. `save_candles(out_dir, ...)` merges into `<run folder>/<SYMBOL>/<year>.<csv|parquet>`, splitting by year, deduplicating on `date` (tz-naive IST) and sorting, with an atomic temp-file replace. `read_year()` / `write_year()` handle the two formats; CSV dates are written as `YYYY-MM-DD HH:MM:SS` for minute data and `YYYY-MM-DD` for daily. Columns: `date, open, high, low, close, volume, tradingsymbol, instrument_token`. Spaces in symbols become `_` in the folder name (`NIFTY 50` -> `NIFTY_50`) while the `tradingsymbol` column keeps the real name; reserved Windows names get a `_` suffix. `progress.sqlite` and `errors.log` live in the save folder itself (next to the run folders), so resuming needs the same save folder. Data from before run folders existed sits in `<folder>/<interval>/<SYMBOL>/` and is left alone. The default `data/` is gitignored.
  - `POST /browse-folder` opens a native folder dialog by running tkinter in a subprocess (`BROWSE_SCRIPT`), which keeps Tk off Flask threads. It works because the server and the browser are on the same machine.
  - Dashboard (`success.html`): a planner card (Stocks checkbox list with nested trade-to-trade / ETF switches, interval switch, date presets incl. "Since 2015", speed slider, folder with Browse, CSV / Parquet switch) whose JS mirrors the server checks and `make_chunks()` / `job_run_key()` for a live estimate and window ruler; a live card (progress ring, current part, run folders under "Saving to", throughput sparkline computed from `requests` deltas between polls, stat tiles, run details, Stop); and a scrollable list of every stock and index completed in the current job. It polls `/download/status` every 2 s. `JOB["completed"]` is sent incrementally by `/download/status?since=<n>` as `completed_new` (plus `completed_count`) and reset per job via `job_no`. Start / Stop / Browse use `fetch`; start reads `?error=` from the redirect URL and shows toasts. The start button reads "Resume download" when the form matches a partly done run in `JOB`. The tab title shows the percentage while a job runs.
  - Job state lives in memory (`JOB`), so any server restart stops the job. Resume is safe. `job_begin(**fields)` in `job.py` starts every job: it refuses if one is running, resets `COUNTERS`, sets `state="running"` and bumps `job_no`. `JOB["kind"]` is `"backfill"` or `"fno"`. An F&O job leaves the planner's keys (`from`, `to`, `interval`, `format`, `equity`, `indices`) alone, so the planner form keeps its values.
- Daily F&O job (`backfill/fno.py`, `run_daily`):
  - `UNDERLYINGS = {"NIFTY": ("NFO", 50), "SENSEX": ("BFO", 100)}` (Kite exchange, strike step for ATM) and `EXCHANGE_OF = {"NIFTY": "NSE", "SENSEX": "BSE"}` (`exchange_name()`: whose bhavcopy checks it; messages say NSE/BSE from it). Every function takes `underlying`; SENSEX goes to `SENSEX_FnO_1min/`, run key `fno:SENSEX:BFO:<date>`, its own lock. The dashboard's F&O card has an Index switch (NIFTY | SENSEX, `boot.fno.underlyings`, `und` state in `App`, remembered in localStorage `fno-underlying`) that also drives `Q.underlying` for the `BhavCard` and every `/fno/*` call; the CLIs take `--underlying SENSEX`. Dhan does NIFTY and SENSEX too (`dhan.UNDERLYINGS`; `fno.exchange_of(u, "dhan")` is NSE_FNO / BSE_FNO, so Dhan SENSEX goes to `SENSEX_FnO_1min_Dhan/`, run key `fno-dhan:SENSEX:BSE_FNO:<date>`, `instruments_BSE_FNO.csv`, and its trim uses BSE's bhavcopy; the Dhan page shows the same Index switch). Output goes to `<save folder>/<UNDERLYING>_FnO_1min/<date>/{futures,options}/`, plus `instruments_<EXCH>.csv`, `summary.csv`, `run.log`, and `holidays.log` one level up.
  - Everything date- or time-related uses `IST = ZoneInfo("Asia/Kolkata")` explicitly (`now_ist`, `today_ist`, `to_ist`), never local time, because the server may run on UTC. The run date is always picked by the user: the dashboard's date picker starts empty, the route requires `date`, `date_from`+`date_to` (or `missing=1`), and the CLI requires a date or `--missing`. Never default it to today. `too_early()` refuses today before `READY_AT` = 15:40.
  - Date window (`date_window`, `window_error`): allowed dates are [previous expiry + 1, today], because on those days every contract is still live, so the day is complete. There is no PARTIAL marking; dates outside are refused (`"outside_window"`, CLI exit 3). Current week expiry = earliest live expiry in today's dump (`live_expiries`). Previous expiry = latest expiry in `expiries_seen.csv` (`read_expiries`/`record_expiries`; seeded from saved `instruments_*.csv` dumps if missing) before the current one. Falls back to `weekday_before(current, weekday)` (`config.weekly_expiry_weekday(underlying)`: .env `WEEKLY_EXPIRY_WEEKDAY_<UNDERLYING>`, for NIFTY also the older `WEEKLY_EXPIRY_WEEKDAY`; defaults `WEEKLY_EXPIRY_DEFAULTS` NIFTY TUE, SENSEX THU), with `estimated=True` and a WARNING (`window_note`), when history has nothing on or after fallback - 1 day. That guard keeps stale history from opening the window too early; keep it. `load_window()` fetches the dump, records history and returns the window. `run_daily` checks too_early, then the token (`connect`), then the window, all before creating the day folder.
  - `missing_dates()` lists window dates without a complete day (summary.csv and no non-DONE rows), minus `holidays_logged()` and today before READY_AT. It creates nothing on disk (the dashboard calls it while the user types a folder). `run_missing()` runs them oldest first with one Kite session, dump and window (`run_daily(..., kite=, instruments=, window=, last=False)` keeps `state` running between days). `run_missing(dates=[...])` runs a picked range instead (`range_dates()`): every day in it, saved or not (saved contracts are skipped), minus logged holidays and today before READY_AT; a day outside the window refuses the whole range (`"outside_window"`), and messages say "Range days".
  - Dashboard: `GET /download/fno-window?folder=` (`fno_window()`, live expiries cached per IST day in `LIVE`; it reads the folder's history but writes nothing) feeds the card: date min/max, current week expiry, the expiry-day warning, and the missing days for the "Download all missing days" button. `POST /download/fno-start` takes `date`, a range `date_from`+`date_to` (`fno.parse_pick()`; the same day twice is one day; first/last day must pass `window_error`, last day `too_early`; run key `fno:NIFTY:NFO:<from>_to_<to>`, `fno_date` ""), or `missing=1`, `speed`, `folder`, `keep_zero=1|0`, and `refetch=1` (with a single date: `refetch_no_trade`; refused with a range or unless `keep_zero=1` and the day has summary.csv).
  - Cross-process lock: `acquire_lock()` takes an OS lock (`msvcrt.locking` past EOF / `fcntl.flock`) on `<UNDERLYING>_FnO_1min/.lock`. It is held by both the CLI and the dashboard thread and dropped by the OS if the process dies. Do not switch to PID files (`os.kill(pid, 0)` terminates the process on Windows).
  - Order: too_early, `kite.profile()` token check (`TokenException`/`PermissionException` -> `"auth_failed"`), the instrument dump and window check (all before the day folder is created), `select_contracts()` (`name == underlying`, FUT/CE/PE, expiry >= date), names, then the holiday check (the nearest future returns no candles and, on Kite, so does the spot index (`spot_traded()`: Kite `SPOT_TOKENS` NIFTY 50 256265, SENSEX 265; Dhan `DhanClient.spot_token()`; asked only when the future is empty, because a SENSEX future can go a trading day untraded) -> log it, delete the day folder only if this run created it and it has no contract CSVs, return `"holiday"`), then every contract via `fetch_chunk(..., oi=True, max_tries=3)` over `WINDOW` 09:00-16:00 (all rows kept), plus one retry pass for FAILED, then `build_summary()`. Kite and Dhan runs then get the day's bhavcopy (`run_daily(bhav_check=)`, default `fno.AUTO_BHAV and not refetch`; on Dhan the trim's saved download is reused): `fetch_day_bhav()` reuses `bhav.listed_names()` (saved file, else a download of at most `bhav.CHECK_BUDGET` = 60 s, saved into `<day>/bhavcopy/`); then `check_day_bhav()` runs `bhav.check_saved()` after summary.csv is written. Not published / errors: run.log and `bhavcopy.log` get the reason, the day stays pending, and the run's status never changes. `tests/conftest.py` sets `fno.AUTO_BHAV = False` for every test; tests that need it turn it on and stub `bhav.fetch_bhav`. `SUMMARY_COLUMNS`: `Listed_strikes`/`Listed_contracts` come from the dump; `Traded_strikes`/`CE_files`/`PE_files` are counted from the files on disk at the end (so resumed runs count earlier files), never from this run's writes.
  - Names come from expiry/strike (`contract_name`), never from Kite's tradingsymbol. A naming error (non-whole strike) marks that contract FAILED. Duplicates never overwrite (feature 26): contracts sharing a tradingsymbol or building the same file name are all FAILED with reason `DUPLICATE_NAME` before any request (logged in run.log and errors.log), and `save()` refuses to write a path another contract already wrote this run (`DuplicateWrite`: the earlier file is removed and both are FAILED `DUPLICATE_NAME`). Progress is kept in `progress.sqlite` under run key `fno:<UNDERLYING>:<EXCH>:<date>`, keyed by tradingsymbol. A contract is skipped if it is DONE or its file exists. Contracts with no candles never get a file (`JOB["empty"]`, reason `NO_CANDLES`). Kite builds volume from differences of the day's cumulative volume, so a contract that traded once can come back with candles (right price and OI) whose volumes are all 0 (verified 2026-10-12: all 56 MISSING_IN_KITE contracts of 2026-10-07). "Keep zero-volume contracts" (`keep_zero`; default `config.KEEP_ZERO_VOLUME`, .env `KEEP_ZERO_VOLUME` ON/OFF overrides; dashboard switch, CLI flags) writes those rows exactly as Kite returns them; OFF gives no file and reason `ZERO_VOLUME`. Counts: `JOB["zero_kept"]` / `JOB["zero_skipped"]`; both modes list them in `<date>/zero_volume_contracts.csv` (`ZERO_VOLUME_COLUMNS`, merged across runs). The reason is stored in the `reason` column of `chunks` (added by `open_db`; NULL for older days). With keep_zero ON a run re-requests DONE contracts without a file whose reason is ZERO_VOLUME; `refetch_no_trade()` (dashboard "Re-check no-trade contracts", `--refetch-no-trade`, needs ON and a saved day) re-requests every DONE contract without a file whatever its reason, then runs `bhav.check_saved` if the bhavcopy is saved. run.log records the setting, and summary.csv's last column `Keep_zero_volume` holds the last run's setting (kept by `rewrite_summary`).
  - CSV: `HEADER` `Ticker,Date,Time,Open,High,Low,Close,Volume,OI`, LF line endings, `Date` as YYYYMMDD, `Time` as HH:MM:SS IST, numbers via `fmt_num` (whole floats without `.0`), matching the user's Accelpix files.
  - The live card reuses the backfill keys (`stocks_*`/`chunks_*` = contracts, `completed` = files written) plus `fno_date`, `fno_underlying`, `fno_exchange`, `fno_summary` (summary.csv rows) and `fno_futures` (per-future stats). The dashboard's `FnoCard` has its own save folder (`fnoFolder` state in `App`, shared with `BhavCard`; input `#fno-folder` plus Browse via `/browse-folder`), started from `boot.form.folder`; the planner's `folder` state lives in `App` and is not shared with it.
  - A past day's dump is saved as `instruments_<EXCH>_fetched_<today>.csv` because it is today's list.
  - `backfill/fno_loader.py` reads saved days back for backtests: `load_day`, `load_contract` (minute bars; `fill_oi()` per file: OI 0 in a contract with non-zero OI that day becomes NaN and is forward-filled from the previous minute, `OI_filled` True on those rows, leading zeros stay NaN, all-zero days untouched, never across days; `fill_oi=False` gives raw values; files are never written) and `load_eod` (the saved bhavcopy by our contract names: `EOD_COLUMNS` with Close, Last, Settle, OI in shares, Volume_contracts, Lot). Backtests should take the EOD close, settlement price and final OI from `load_eod`, not from Kite's last bar.
- NSE F&O bhavcopy check (`backfill/bhav.py`, `run_bhav`):
  - Per exchange (`SOURCES`, `bhav_url(run_date, underlying)`; `fetch_bhav(..., underlying=)`, which every caller passes by keyword): BSE (verified 2026-10-13) is `BSE_BHAV_URL` (`www.bseindia.com/download/Bhavcopy/Derivative/BhavCopy_BSE_FO_0_0_0_<YYYYMMDD>_F_0000.CSV`), a plain CSV (not a zip) with the same `BHAV_HEADER`, Src BSE, TckrSymb SENSEX (BANKEX rows filtered out), volume AND OI in shares (`SOURCES[...]["volume"]`: the volume unit defaults to 1 without traded futures; `load_eod` divides by the lot for `Volume_contracts`); no home-page warm-up, Referer bseindia; a day not published comes back as 200 with BSE's HTML page, which raises `BhavNotAvailable` like NSE's 404 (a body starting with `TradDt` is the file). Saved as `<underlying>_bhav.csv` (`sensex_bhav.csv`) next to the original file; exports of a SENSEX check end in `_sensex`.
  - NSE source (verified UDiFF format, 2026-10-09): `BHAV_URL` (`nsearchives.nseindia.com/content/fo/BhavCopy_NSE_FO_0_0_0_<YYYYMMDD>_F_0000.csv.zip`) returns 200 without cookies; the `www.nseindia.com` home page answers scripts with 403 and that is ignored (`fetch_bhav`, 3 tries, 404 -> `BhavNotAvailable`, which only appends to `<UNDERLYING>_FnO_1min/bhavcopy.log`). Header in `BHAV_HEADER`; ISO dates. Rows: `TckrSymb == underlying`, `FinInstrmTp` IDF/IDO, names via `fno.contract_name`.
  - Units: `TtlTradgVol` is in contracts, `OpnIntrst` in shares, so `detect_unit()` finds the volume and OI multipliers separately from the futures (snapped to 1 or the lot).
  - Output in `<date>/bhavcopy/`: the original zip, `nifty_bhav.csv`, `bhav_compare.csv` (`COMPARE_COLUMNS`) and `bhav_check.json` (status, counts, severity), plus `write_bhav_summary()`: `bhav_summary.csv` (`SUMMARY_FILE_COLUMNS`: an `ALL` row with Date, Status and units, then one row per expiry and FUT/OPT; no per-difference files are written any more (old days may still have them; nothing reads them)), and `write_days_summary()`: `checked_days_summary.csv` (`DAYS_SUMMARY_FILE`), this day's row only, in the columns of the "All days summary (CSV)" download (which still lists every checked day; every file in a day's bhavcopy folder holds that day only; other days' copies are not rewritten; broker from the folder name, Dhan columns relabelled; skipped while no day has summary.csv). `check_saved()` re-runs the comparison from the saved file without network access (after `run_bhav` saves a download, after a re-download, and for `nifty_bhav.py DATE --bhav-file`). The check takes the same lock as the Kite job.
  - Statuses from `compare()` (combined with `+`): OK / MISSING_IN_KITE / EXTRA_IN_KITE / BAD_NAME / ZERO_VOLUME_IN_KITE (file with total volume 0, bhavcopy volume > 0: counted in `zero_volume`, a volume difference not a missing contract; always amber, even with VOLUME_DIFF) / VOLUME_DIFF (>1% AND >5 lots: `VOLUME_TOL`, `VOLUME_MIN_LOTS`) / OI_DIFF (>3%, `OI_TOL`: Kite OI is an intraday snapshot) / PRICE_DIFF (`LastPric` vs the close of Kite's last bar of the day only, within max(0.5%, 2 ticks)). Kite labels candles by start time, so the 15:30 candle is post-close; `Kite_last_regular` (last bar with Time < `REGULAR_END` 15:30) is for reference only. `Last_bar` is the last bar's time, and `Note` = "trades after Kite's last bar" when the price differs and that bar is before `LATE_BAR` 15:40. Futures `ClsPric` is never compared.
  - Buckets (`bucket_namer()`): options use `fno.bucket_labels`; futures are Current month / Next month by expiry order; the rest are `FAR`. It works from the expiries in the bhavcopy plus `parse_name()` of the files on disk, so EXTRA rows absent from the bhavcopy also get Expiry/Type/Strike/Bucket. Counts add `liquid_missing`, `liquid_diffs`, `liquid_volume_diffs` and `far_problems`; `check_status()` appends `; liquid buckets: X missing, Y diffs`.
  - Severity (`severity()`, stored in `bhav_check.json`): `major` (red) only for MISSING_IN_KITE in any bucket or a VOLUME_DIFF over the limits whose Kite volume is > 0 (`missing` + `red_volume_diffs`); everything else is a known Kite limitation and `minor` (amber, "CHECK (minor)") in every bucket, liquid included: ZERO_VOLUME_IN_KITE, EXTRA_IN_KITE, OI_DIFF, PRICE_DIFF (with or without "trades after Kite's last bar"); "" when OK. Buckets (`liquid_*`, `far_problems`) are for display only. `day_severity()` re-derives it from the counts (checks before `red_volume_diffs` use `volume_diffs`: no zero-volume files existed then); checks without those counts map `liquid`->major and `far`->minor (`OLD_SEVERITY`), or count as major. Grouping and colour must never drop a difference: totals, statuses and exit codes keep every one.
  - `summary.csv` carries `BHAV_SUMMARY_COLUMNS` plus one `Futures` row per future expiry; `fno.summary_rows()` recomputes them from the saved `nifty_bhav.csv` on every Kite run (so a re-run keeps the check) and `fno.rewrite_summary()` rebuilds summary.csv from the saved instrument list after a check.
  - `diff_rows()` returns non-OK rows sorted by bhavcopy volume descending, with `Bhav_volume_shares`, `Live` and `Liquid`; for old compare files without Bucket (or with the old price columns) it compares again in memory.
  - Dashboard routes, all JSON and synchronous:
    - `GET /fno/bhav-status` returns `list_days()` (saved days newest first, `ok`/`diffs`/`pending` plus severity) and `banners()`: `check` (major days among the last 10, red), `minor` (amber) and `pending_old` (pending days before yesterday, yellow, with "Check all pending").
    - `GET /fno/bhav-diff` returns the day's non-OK rows from `diff_rows()`, with `Bhav_volume_shares` and `Live` = expiry >= today.
    - `POST /fno/bhav-check` takes `date` or `missing=1` and returns per-day results.
    - `POST /fno/redownload` runs `fno.redownload_contract()` for one live contract (lock, rate limit, Kite token, or with source=dhan the same checks as a Dhan download: `token_ok`, then `data_plan_error(profile())`; `keep_zero=1` keeps zero-volume candles), then `check_saved`.
    - `GET /fno/bhav-export?scope=days|view|all|xlsx[&date=&bucket=]` sends `bhav_export.export()` as an attachment: the all-days summary (`DAY_COLUMNS`, checked days only), the difference list for a bucket filter (`all`/`liquid`/a bucket name, in the panel's order), every contract of the day, or the Excel report (sheets `SHEETS`: Summary with the day row and per-expiry rows, frozen at A5; Not OK; All contracts; Settlement; header frozen, autofilter, fitted widths). Contract rows use `CONTRACT_COLUMNS` (the panel's "bhav / Kite" pairs split, plus `Bhav_volume_shares`). It reads `bhav.compare_rows()` (the saved bhav_compare.csv, re-compared in memory only for files without Bucket), bhav_check.json and summary.csv, writes nothing, and returns 404 when the day (or every day) has no check. Values stay raw (`fmt_num`, no thousands separators); Excel gets numbers as numbers and dates/times as text.
    - Writing routes refuse while a job runs or the lock is held (`locked_fno`). Read routes never create the folder.
  - UI: `BhavCard` sits in a full-width row (`.full-row`) under both columns, so its tables show every column. Day rows are tinted by severity (`day-ok` / `day-diffs` / `day-minor` / `day-pending`) with a Liquid buckets column; the Volume diffs cell adds "N zero-volume" when `counts.zero_volume` > 0. The diff panel has a bucket filter (view only; the count line shows "n of N"), and Re-download for live contracts. `DownloadMenu` (a "Download ▾" button with a small menu) fetches `/fno/bhav-export` and saves the blob under the Content-Disposition name, so a missing check gives a toast, not an error page: "All days summary (CSV)" next to the day table; "This view (CSV)" (current bucket filter), "All contracts for this day (CSV)" and "Full report (Excel)" above the diff panel.
  - The F&O card and the `BhavCard` share `fnoFolder` and `keepZero` (the "Keep contracts with candles but zero volume" switch, starting from `boot.fno.keep_zero_volume`), which live in `App` along with the bhav day list and the banners. They are separate from the planner's `folder`. The card's date picker (`DayRangePicker`, inline calendar limited to the window, amber dot = missing, green = saved) picks one day with one click or a range with a second click; `/dhan/fno-start` accepts the same range fields. For a range, "Check vs NSE bhavcopy" checks each saved day in it and Re-check no-trade is hidden. The F&O card shows "Re-check no-trade contracts for <date>" for a saved day (enabled only with the switch ON). For F&O jobs the live card shows "No candles, no file" (`empty`) and "Zero-volume candles" (`zero_kept` + `zero_skipped`, with "kept N / skipped N") tiles instead of "Time left" (the ETA shows by the ring), and "Zero-volume contracts: Kept (ON) / Skipped (OFF)" (`JOB["keep_zero"]`) in the run details.
  - All checks are started by hand; no cron.
