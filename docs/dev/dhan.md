# Dhan

Dhan as a second F&O source: sign-in with a pasted token, the Dhan F&O page, and `DhanClient`, the
Kite-shaped DhanHQ v2 client the F&O job runs on (`source="dhan"`).

## Dhan sign-in
- Dhan sign-in (`dhan.py`, `dhan_login.html`): the user pastes a Client ID and an access token generated on web.dhan.co (no API key / redirect flow). `POST /dhan/login` (blank token with unchanged Client ID re-checks the saved one) calls `dhan_api.fetch_profile()` (`GET https://api.dhan.co/v2/profile`, header `access-token`); the returned `dhanClientId` must equal the entered Client ID. It saves `DHAN_CLIENT_ID`, `DHAN_ACCESS_TOKEN` and `DHAN_TOKEN_EXPIRY` (`parse_validity()` turns Dhan's `tokenValidity` "DD/MM/YYYY HH:MM", IST, into ISO); `session["dhan_user"]` holds client id and `dataPlan` (not the token). Then `/dhan/dashboard?dhan=1`. `/dhan/logout` removes the token keys locally only. `dhan.status(env)` (connected = token present and expiry, IST, in the future) feeds the Dhan pages and the Kite dashboard's account menu (`boot.dhan`, with "Open Dhan F&O"); the Kite dashboard passes its own `load_env()` so tests' stubs cover it. Errors never include the token. Kite and Dhan sessions are independent; `/browse-folder` accepts either.

## Dhan F&O page
- Dhan F&O page (`/dhan/dashboard`, needs a valid Dhan token): renders `success.html` with `mode="dhan"` and `broker` (`name`, `maxSpeed` 5, `defaultSpeed` 4, `urls.fnoWindow`/`fno`/`page`); in that mode `App` shows `FnoCard` + `Live` + `Feed` + the banners and `BhavCard` (no Planner), a `DhanMenu` plus a visible Log out button (`.nav-actions`, `/dhan/logout`), and `FnoCard` shows the same rows and buttons as on Kite (Re-check no-trade included; terminal hints add `--source dhan`). Every bhavcopy fetch sends `Q` (`underlying` plus `source: "dhan"` on the Dhan page), and `brand()` shows Kite wording from the check (lines, statuses, headers) as Dhan there. Kite mode passes `broker` with the Kite URLs and max 3, so it renders as before. The F&O card's texts are the same in both modes (broker name from `B.name`); the brokers differ only in Dhan's speed limit, data-plan check and folder (the trim to the bhavcopy is the same setting on both). `dhan.py` passes `weekly_expiry_weekday(underlying)` like the Kite routes. `/dhan/fno-window` (live expiries from Dhan's list, cached per IST day in `dhan.LIVE`, history from the Dhan folder) and `POST /dhan/fno-start` (`date`, `date_from`+`date_to`, `missing=1`, or `refetch=1` with the Kite route's refusals, `speed` 0 < s <= 5, `folder`, `keep_zero`, `trim_bhav`; checks the token and refuses unless the profile's data plan is Active, then window/too_early, lock, `job_begin`) run `fno.run_daily` / `run_missing` / `refetch_no_trade` in a thread with `kite=DhanClient(token)` and `source="dhan"`. The token rule (`dhan_api.token_connected`/`token_ok`) and the plan check (`data_plan_error`) live in `backfill/dhan_api.py` so the CLI shares them without Flask. Stop and status reuse `/download/stop` and `/download/status`.

## DhanClient
- `backfill/dhan_api.DhanClient` implements what the F&O job uses from KiteConnect: `profile()`, `instruments(exchange)` (Kite's NFO/BFO mapped by `SEGMENT_OF` to `GET https://api.dhan.co/v2/instrument/NSE_FNO` or `/BSE_FNO`; each row's `exchange` is the segment, and `historical_data` sends the segment remembered per security id, also learned by `learn()` from a saved list; FUTIDX/OPTIDX rows as Kite-style dicts: `name`=UNDERLYING_SYMBOL, FUT/CE/PE from OPTION_TYPE, `expiry` from SM_EXPIRY_DATE, `strike`, `tradingsymbol`=`SYMBOL_NAME#SECURITY_ID` (Dhan's SYMBOL_NAME is the same for every expiry of a month, e.g. `NIFTY-Oct2026-25000-CE` for 13, 19 and 27 Oct; keyed by it alone, weeklies were written into the monthly file on 2026-10-07), `instrument_token`=SECURITY_ID; missing columns raise a clear error) `spot_token(underlying)` (`SPOT_IDS` NIFTY 13, SENSEX 51 on IDX_I, instrument INDEX; for the holiday check) and `historical_data()` (`POST https://api.dhan.co/v2/charts/intraday`, `interval` "1", `oi`, IST "YYYY-MM-DD HH:MM:SS" bounds; column arrays turned into candle dicts with IST datetimes). Errors are raised as kiteconnect exceptions so `fetch_chunk` treats them like Kite's: 401/DH-901 TokenException, DH-902 PermissionException (both stop the job), 429/DH-904 code 429 (rate halves), 5xx/DH-908 NetworkException (retry), DH-907/"no data" -> no candles, other 4xx InputException (contract FAILED).
